# Supermarket：代码理解与面试讲解

这份说明对应当前仓库源码，目标是帮助你解释已有实现，而不是增加功能清单。
分工依据你的说明：“基本上样式和测试是 AI 写的”，以及本次协作记录。业务主体由你完成；AI 主要辅助样式、测试，并在本轮参与具体修复和文档整理。

## 1. 60–90 秒项目介绍

> 这是一个用于展示全栈开发能力的超市购物与管理项目。
> 前端使用 React 和 TypeScript，后端是 ASP.NET Core 10，使用 EF Core 访问 SQL Server。
> 管理员界面可以维护商品、分类和厂商，并查看销售统计；顾客可以浏览商品、加入购物车、结账和查看自己的订单。
> 身份认证使用 ASP.NET Core Identity 和 Cookie，商品管理与订单接口按角色授权。
> 结账时客户端只提交商品 ID 和数量，服务器重新读取价格和库存，在事务中扣减库存并保存订单明细。
> 项目还接入 Azure AI，根据数据库中有库存的商品生成推荐或购物清单；后端会重新验证商品、数量和金额。
> 当前结账是模拟支付，购物车保存在页面内存中，AI 每次只发送当前问题和商品上下文。
> 项目的主要业务功能由我完成，包括用户登录注册、商品管理、购物车和订单等流程。
> 样式和测试主要使用 AI 辅助实现；后期也借助 AI 排查部分问题。我负责确定需求、功能范围和界面方向，并根据实际效果持续调整。
> 已有测试覆盖部分业务分支和页面行为，但还不能证明真实 SQL Server 下的并发结账安全。

介绍时区分自己完成的业务主体与 AI 协助的工作。对某个细节尚未理解，可以说明正在补充学习，不要把 AI 生成的实现说成自己当时独立推导的结果。
部署配置存在也不代表网站现在可访问；不要声称未核实的在线状态、用户量或性能数字。

## 2. 先理解一条完整的数据流

```text
顾客点击 Add to Cart
  → userOrder.tsx 更新 React cart 状态
  → 点击结账，checkOutApi.ts 发送商品 ID / 数量
  → Cookie 随请求进入 ASP.NET Core
  → 身份认证与角色授权
  → OrderController.Checkout 验证输入
  → EF Core 在 SQL 事务中读取商品、扣库存、写订单和明细
  → 返回 orderId / totalAmount
  → 前端清空购物车、刷新商品列表，可打开 My orders
```

前端负责交互和即时提示；后端负责可信的业务判断；数据库负责持久化。
这是一个前后端分离开发、可由后端同时提供静态网页和 API 的应用，没有必要包装成微服务。
开发时 `frontend/vite.config.ts` 把 `/api` 代理到本机后端；API 地址在前端多为相对路径。
`Program.cs` 提供静态文件和 React 路由回退，并避免未知 `/api` 地址落入网页 HTML。

## 4. 身份认证、角色授权和页面检查

认证回答“你是谁”：`PasswordSignInAsync` 登录，`SignInManager` 管理 Cookie 会话。
前端请求设置 `credentials: "include"`，后端通过当前身份读取用户，而不是相信浏览器提交的用户 ID。
`/api/auth/me` 返回当前用户和角色，`ProtectedRoute` 据此决定渲染页面还是跳到登录页。
授权回答“你能做什么”：由后端 `[Authorize]` 和 `[Authorize(Roles = "...")]` 执行。
隐藏按钮或阻止页面导航只能改善体验，不能阻止别人直接发 HTTP 请求。

| 当前接口 | 源码中的保护 |
| --- | --- |
| 商品读取 | Admin 或 User |
| 商品新增、修改、删除；用户管理；销售统计 | Admin |
| checkout | User，同时在方法中显式拒绝 Admin |
| mine | User，查询再按当前身份中的用户 ID 过滤 |
| 管理员查询指定用户订单 | Admin |
| 分类、厂商读取 | Admin 或 User |
| 分类、厂商新增、修改、删除 | Admin |
| AI chat | User |

检查权限时应逐个核对控制器和操作上的授权声明，不能只看 `App.tsx` 的页面分区。
`Program.cs` 没有要求所有请求登录的全局授权策略，具体接口的授权声明尤其重要。
新账号注册后分配 User；`IdentitySeeder` 创建 Admin/User 角色，开发环境可按配置提升指定已有账号。
不要把管理员页面地址当成权限来源，也不要把“有 Cookie”理解为“具有 Admin 角色”。

## 5. 数据模型与结账：重点讲清可信边界

`Product` 保存商品价格、库存及分类/厂商关联；`Order` 保存用户 ID、时间、状态和总金额。
`OrderItem` 保存商品 ID，并保存购买时的名称、单价、数量和行金额。
这些快照用于展示历史订单，商品后来改名或改价不会让已有明细重新按现价计算。
`AppDbContext` 继承 `IdentityDbContext<ApplicationUser>`，业务表与 Identity 表共用上下文。

假设数据库里某商品 ID 为 7，单价 £2.50，库存 5；这是说明算法的例子，不代表现有种子数据。
客户端购物车可能显示名称与单价，但真正请求形如：

```json
{"items":[{"productId":7,"quantity":2}]}
```

服务器重新取商品价格，计算 £5.00，库存由 5 变成 3，并保存订单明细。
浏览器篡改显示价格不会改变结账依据；库存变化后，页面上的旧库存也不能保证购买成功。

`Checkout` 的关键步骤：

1. 检查当前用户、空购物车、非正数 ID/数量。
2. 合并重复商品 ID，用 `long` 累加并拒绝超过 `int.MaxValue` 的数量。
3. 在 EF 执行重试策略内部开启 `Serializable` 事务。
4. 按商品 ID 排序读取，检查存在与库存；扣库存并以数据库价格构建明细。
5. 一次 `SaveChangesAsync` 后提交事务，再返回成功信息。

订单写入和库存更新处于同一事务；未提交就退出时，事务释放会回滚数据库操作。
固定商品访问顺序有助于减少锁顺序冲突；`Serializable` 更强的隔离也可能增加等待或死锁。
不要因此承诺“绝不会超卖”“支持多少并发”：需要真实 SQL、多请求竞争、失败重试等验证。
执行策略支持瞬时故障重试，但源码没有结账幂等键；网络失败后的重复提交仍是待验证边界。
特别是提交结果不确定时的重试，以及同一 DbContext 跟踪状态，都不能靠一句“有事务”带过。
`Status = "Paid"` 直接由后端设置，没有支付服务扣款或支付回调：这里是模拟支付。

## 6. AI：模型提供候选，业务代码决定能展示什么

`AiController` 先验证问题非空、长度不超过 500，再读最多 100 个有库存商品，按 ID 排序。
`AzureAiService` 将商品 JSON、当前问题和规则发送给 Azure 的 `/responses` 接口。
密钥从后端配置读取；前端通过自己的 `/api/ai/chat` 调用，不应获得 Azure 密钥。
请求没有传聊天历史、会话 ID 或 `previous_response_id`；页面虽显示历史，每次模型调用仍是独立请求。
这属于将实时商品数据放入提示词的上下文增强，没有向量库检索或自训练模型实现。

提示词要求 JSON 只是约定，真正的检查在 `AiController`：

- 解析 JSON 并检查对象、数组、数字等类型；解析失败或服务失败返回 502。
- 推荐 ID 只与刚查询出的真实商品集合匹配，忽略不存在的 ID。
- 清单数量必须是正整数；合并重复 ID，并将数量限制在库存内。
- 名称、价格、库存来自数据库查询结果；总金额由服务器重算。
- 若模型返回有效非负预算，按商品遍历顺序缩减数量，使清单不超过该预算。
- 清单回复文本由后端重新生成，避免文字仍描述被缩减前的数量。

例：模型推荐 ID 999 和 ID 7，但数据库上下文只有 ID 7，则 999 会被过滤。
如果 ID 7 库存为 3，模型要求 20 件，服务器最多保留 3 件，再做预算检查。
这不是最优购物组合算法；预算字段也由模型提取，并非服务器独立解析用户原话。
普通推荐的自然语言回复仍由模型生成，不能声称所有文字事实都经过严格验证。
AI 清单不会预留库存；用户加入购物车后，最终仍要走结账时的数据库校验。

## 7. 测试覆盖和可以诚实说出的结论

| 已有证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| `CheckoutTests.cs` | 空购物车、无效数量/ID、缺少身份、Admin 拒绝分支 | 成功扣库存、事务提交、多人抢库存 |
| 订单/销售统计测试 | InMemory 数据下筛选、排序、汇总的预期 | SQL 翻译、真实事务与锁行为 |
| `MyOrdersTests.cs` | 当前用户隔离、Paid 筛选、明细和时间格式 | 完整 Cookie 登录和授权管道 |
| `AuthorizationTests.cs` | 真实控制器路由和授权管道下，匿名请求被拒绝、顾客不能管理分类和厂商、AI 限顾客访问 | 测试身份替身不等于真实 Cookie 登录，InMemory 不等于 SQL Server |
| `aiChat.test.tsx` | Mock API 下数量编辑、加购回调和金额显示 | 真正模型输出、后端 AI 校验正确性 |
| `dashboard.test.tsx` | Mock 数据下卡片、低库存提示和错误显示 | 真实后端统计或部署可用性 |

直接调用控制器方法不会运行 ASP.NET 授权中间件，所以不能把它说成完整权限集成测试。
Checkout 测试虽然配置了 SQL Server Provider，但所测分支在连库前返回；这不是 SQL 并发验证。
`basic.test.ts` 的 `1 + 1` 只验证测试环境，不提供业务保证。
前端 `npm test` 依次运行 `test/` 中的 Node 测试和 `src/test/` 中的 Vitest 测试；也可单独运行 `npm run test:unit` 或 `npm run test:vitest`。
`scripts/verify-local-demo.mjs --checkout` 另可在本地真实 API/SQL 数据库中验证一次模拟购买、库存减少、订单保存和 Cookie 退出；会新增一个订单并使用一件库存。
一次成功的本地购买仍不是并发或不确定提交后的重试验证。测试“存在”和某次“已通过”也是两件事；运行证据见 `docs/demo-readiness.md`。

## 8. 八个常见面试问题

**1. 这个项目里你具体做了什么？**
主要业务功能由我完成，样式和测试主要有 AI 辅助；本轮 AI 还协助修复了会话退出、错误提示和接口权限等问题。
我可以用一条业务流程解释自己的代码，再明确指出 AI 参与的文件和改动。描述排错时，按实际经历区分“自己定位”和“AI 帮助定位”。

**2. 为什么前端和后端都检查权限？**
前端根据 `/me` 改善导航体验，后端才是安全边界；直接请求 API 也必须授权。
可举商品、分类、厂商写接口的 Admin 限制，以及 `mine` 的用户身份过滤为例。

**3. 为什么不用客户端价格结账？**
客户端可被修改，价格与库存也会变化；请求只发 ID 和数量，服务器重新读取并计算。
明细保存购买时的快照，因此历史订单不依赖商品当前价格。

**4. 两个人同时买最后一件商品怎么办？**
现有实现使用 Serializable 事务，意图让库存读取、校验与扣减保持一致。
更强隔离会产生锁竞争；目前测试不能证明真实 SQL 并发行为，需要承认验证边界。

**5. AI 编造商品或超预算怎么办？**
后端过滤不在真实集合中的 ID，以数据库价格、库存重建清单并校验模型给出的预算。
提示词不是保证；普通文字、预算提取和商品适配性仍有模型局限。

**6. 聊天记录和购物车存在哪里？**
都在 React 状态中；刷新会丢失。聊天历史只用于页面显示，每次请求没有传完整历史。
订单结账后才持久化到数据库，购物车状态与历史订单是不同的数据。

**7. 你写了什么测试，能保证什么？**
只对自己真实写过的测试使用“我写了”；可解释负面输入、订单隔离、UI Mock 测试的价值。
不能把 InMemory 或控制器单测包装成真实 SQL 事务、并发或 HTTP 授权证明。

**8. 如果让你继续完善，先考虑什么？**
先解释已有边界的影响，例如结账重试与幂等，以及真实 SQL 集成验证。
这些是理解当前实现后的判断，不代表已实现，也不需要为面试临时堆功能。

练习目标：不看稿沿着“页面 → API → 身份 → 数据库 → 响应”讲一次，再打开代码逐点核对。
